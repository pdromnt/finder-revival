# USB-only maintenance

This is the normal installer/rollback path under development for the exact
[supported baseline](compatibility.md). It needs no soldered console, SSH setup
or bootloader commands. UART remains a recovery option, not a routine step.
Until the hardware gates in [validation](validation.md) pass, this path remains
experimental. PC/container checks do not establish a successful printer trial.
USB-only CHECK, packaged INSTALL and ROLLBACK, each followed by a normal power
cycle, passed on the development printer. The round trip restored its protected baseline.

## Prepare and choose an operation

Use a **16 GB minimum FAT32 USB drive**. Extract the generic USB ZIP to its root,
retaining `0007`, `flashforge_init.sh` and the `revival` directory. Keep the
matching runtime-source archive on the PC. Never distribute your personalized
stick or its reports/backups: they may contain owner keys and settings.

Create `revival/REQUEST.txt` containing exactly one of these lines:

| Request | Action |
| --- | --- |
| `CHECK` | Enter RAM; require clean unmounted root/data checks; install nothing |
| `BACKUP` | Run those checks, then acquire this printer's storage to USB |
| `INSTALL` | Install the overlay and save this printer's previous managed files |
| `ROLLBACK` | Restore the last successful installation's saved managed files |
| `ROLLBACK usb-REPORT-ID` | Select a particular successful installation report |

`REQUEST.example.txt` contains CHECK as a starting point. The ZIP does not arm an
operation automatically. Without `REQUEST.txt`, the hook retains its diagnostic/
optional temporary-SSH behavior. No shared passwords or private keys are supplied.
If persistent SSH is wanted, add your own ordinary public key as
`revival/authorized_keys` before installing; existing owner authorization is kept.

1. Start with **CHECK**: insert the stick while the printer is off, then power on.
2. Keep power and USB connected until the final screen explicitly says to remove
   USB and power-cycle. A stage can take several minutes; a full backup can take
   an hour or more. There are no touch buttons or automatic reboots.
3. At that completion screen the filesystems and USB have been unmounted. Remove
   the stick, switch the printer off, wait ten seconds and switch it on normally.
4. On the PC, inspect `revival/reports/usb-*/`: CHECK needs `CHECK-PASSED.txt` and
   `FINISHED.txt`, with no `FAILED.txt`. Preserve existing report directories.
5. Before INSTALL, obtain and independently verify your own [backup](backup.md).
   BACKUP needs at least 8 GiB free. Verify every image hash/length on the PC;
   finding a backup folder alone does not establish a complete backup.
6. Write a new request for INSTALL and repeat the off/insert/power-on sequence.
   Review its report, then boot normally without the stick and check operation.

Each request moves into a unique report directory before handoff, so leaving
the stick inserted cannot silently repeat an install/rollback. A failed request
is not automatically retried. Do not re-arm it before reviewing why it failed.
Never run the early-boot entry script from a running printer UI.

## Rollback

The successful install report contains `install/rollback-private.tar`, before/
after file inventories, a private device-identity hash and checksums. Copy the
whole report to the PC. `LATEST-INSTALL.txt` selects the last successful report;
keep the same report with the same printer and package for the trial.

Write `ROLLBACK` to a new `REQUEST.txt` and repeat the USB boot sequence. The
rollback refuses another printer's archive, corrupt reports/archives, symlinks,
unexpected archive paths and managed files edited after installation. It saves
the current managed files externally before restoring the earlier ones, removes
only named files introduced by that installation, and restores startup selection
last. It does not rewrite partitions, kernels, control firmware or print storage.

Owner keys are retained, including credentials first generated by the install;
cloud switches stay OFF. Empty parent directories may remain. This is managed
file/startup rollback, not a byte-for-byte filesystem clone or full uninstall.
If the baseline was stock, its normal logging/update behavior returns: block
Internet access at the router before its next normal boot. If the baseline was
already Revival, rollback returns to that previous Revival setup.

Require `rollback/RESTORED.txt` and the run's `FINISHED.txt` before normal boot.
The [restore runbook](restore.md) covers manual rescue and failures outside this
automated path. Keep the original backup even after a successful rollback.

## How the handoff works

The stock USB hook runs before the GUI/supervisor. Exact BusyBox, inittab, rcS,
auto-run, GUI, kernel and device checks pin the supported behavior. The hook
builds a 16 MiB-capped RAM root from that printer's own binaries/libraries.
A RAM file is temporarily bind-mounted over `/etc/inittab`; the disk file is
never edited. An acknowledgement from the reloaded configuration precedes the
BusyBox init restart signal. A tiny freestanding helper first verifies two
16-byte instruction contexts in the existing PID 1. It changes only the two
`kill(-1, signal)` calls in that process's private RAM, skipping blanket signals
that would also reach the vendor's unprotected SD/eMMC kernel workers. The
on-disk BusyBox is unchanged. The changes disappear when init re-executes our
entry as PID 1; entry failures attempt to restore and verify both words.

The new PID 1 sends TERM/KILL individually only to positive PIDs with a nonzero
userspace address space. It leaves kernel workers alone, records storage state
and verifies a bounded raw read. It then removes the bind, unmounts data, pivots into RAM and
unmounts old root before any offline check or overlay write.

Operations use a separate 4 MiB RAM cap; backups/reports remain on USB. The
kernel, bootloader environment and permanent startup files are untouched by the
handoff. A successful job unmounts root/data and USB before the removal screen.
Nothing automatically repairs a filesystem or tries an unknown stock build.

The init behavior was checked against [BusyBox 1.24.1 source](https://github.com/mirror/busybox/blob/1_24_1/init/init.c)
and rehearsed with that version in an isolated PID namespace. That rehearsal is
separate from the physical CHECK/INSTALL/ROLLBACK evidence in [validation](validation.md).

Earlier physical CHECK attempts completed the pivot but lost eMMC reads after
the original init's blanket signals. Normal boots regained storage access, with
zero recorded ext4 errors. The kernel workers' live `wchan` names matched the
SD/eMMC event threads; both inherited unblocked signals. This is evidence for the
guarded handoff change, not proof that all eMMC driver failures share that cause.
The upstream [Nuvoton eMMC driver](https://github.com/OpenNuvoton/NUC970_Linux_Kernel/blob/master/drivers/mmc/host/nuc970_emmc.c)
also creates its event worker directly with `kernel_thread`.

With the guarded selective shutdown, the next physical CHECK completed both
offline filesystem checks, safely unmounted USB and returned to normal operation
after a power cycle. Protected files matched the pre-trial backup. This supports
the handoff fix on the tested baseline. Packaged INSTALL subsequently passed
with its external rollback archive verified and protected files preserved.
ROLLBACK subsequently restored all protected baseline bytes, removed the single
introduced managed file and passed normal-boot and storage checks. That round
trip returned to the prior Revival setup.
